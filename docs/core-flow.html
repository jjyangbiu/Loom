Loom 核心流程梳理

「对话即生成单页应用」的智能体平台：前端 Vue3 SPA + 后端 FastAPI。

智能体通过工具调用循环在文件沙箱里写文件，生成结果可预览、可迭代、可发布、可克隆。

本文覆盖：① 端到端核心流程　② 智能体循环的控制方式　③ 记忆管理机制

二、首建生成主流程

入口：POST /api/projects/{id}/messages（routers/projects.py 的 send_message）。消息先过限流（每用户每小时额度 + 全局并发，超限 429 并附 Retry-After），再按项目模式和状态阶段分流。

2.1 工程师模式（engineer）

用户首条消息→ 需求澄清 _clarify_stream→ 需求共识卡片→ 确认 /consensus/confirm→ 工程师智能体生成→ 多文件落盘 + 快照

2.2 团队模式（team）—— 五阶段流水线

需求澄清→ 共识确认→ 需求规格 _spec_stream→ 规格确认→ 工单拆解 _break_stream→ 清单确认→ 检查点串行执行

执行阶段（_exec_tickets_stream）：按依赖序逐单执行，每单完成建一个检查点快照，失败可从该单重试（/tickets/resume）。

2.3 关键设计点

设计点说明
确认门（gate）每阶段产物（共识/规格/工单清单）都是待确认卡片；确认接口在项目锁内复查状态，并发双击不会触发两次生成；确认消息以 kind=*_confirm 落对话历史
阶段智能体无文件工具澄清/规格/拆单智能体唯一工具是 submit_* 类结构化提交（解析失败把错误回喂模型自行修正）；只有工程师智能体拥有文件工具
限流只扣一次名额在首条消息时扣定，流水线内的后续阶段（澄清续轮、各确认、拆单）不重复计数
执行期拦截团队模式工单执行期间，普通消息以引导拦截（exec_guide），不污染执行流

三、智能体循环（生成引擎）

核心：backend/app/agent/loop.py 的 run_generation，所有生成阶段共用。

System 提示 + 历史 + 用户输入
  → 模型流式输出（ThinkSplitter 把 <think> 块拆成独立 thinking 事件）
  → 有 tool_calls？
      有 → 沙箱工具执行（write_file / edit_file / read_file / search_templates …）
           → 结果作为 ToolMessage 回喂 → 继续循环（最多 max_steps 步，默认预算 100）
      无 → final_text_hook 收尾核验
           · 返回字符串 → 作为 HumanMessage 回喂，继续循环（防「口头完成」）
           · 返回 None  → yield done，正常出口
  → 循环耗尽 → error(reason="max_steps_exhausted")，路由层据此走兜底收尾

3.1 是否用 LangChain / LangGraph？

循环是手写的：没有 LangGraph，也没有 AgentExecutor。 LangChain 只作「零件级」适配层。
用途是否用 LangChain位置
LLM 客户端（ChatOpenAI + bind_tools + astream）✅ langchain-openaiagent/model.py
消息类型（System/Human/Tool/AIMessageChunk）✅ langchain-coreagent/loop.py
工具 schema 声明（@tool 装饰器）✅ langchain-coreagent/tools.py
Agent 编排 / 状态图 / 循环控制❌ 全部手写loop.py + routers/projects.py

依赖清单只有 langchain-openai、langchain-community，无 langgraph。工具执行也没走 LangChain 的 ToolNode——execute_tool 手写：按名字遍历工具、inspect.signature 校验参数、异常捕获后转成失败文本回喂模型（SandboxViolation 不中断循环）。

3.2 关键控制流技巧

  1. Python 异常做控制流信号：submit_* 工具被执行时抛专用异常（如 _SubmitTicketsInvoked），沿生成器向上传播，由路由层捕获后携 JSON 终止循环——不需要图节点跳转。
  2. final_text_hook 收尾钩子：循环本身不含业务判断；自洽性核验（申报改动 vs 磁盘真实改动）、回喂次数上限等降级链逻辑全部由路由层注入（工单 0025 用纯集合运算取代了早期的中文措辞检测）。
  3. 多阶段编排是数据库推导的状态机，不是图：send_message 按 DB 中消息的 pending 状态分流到不同 _*_stream 函数，每个函数内部各跑一遍 run_generation（各自独立工具集）。
  4. 模型无绑定（鸭子类型）：循环只依赖 bind_tools / astream / ainvoke 约定，测试用 tests/fake_model.py 可编程伪模型走同一接口注入，全链路离线可测。
  5. 重试语义：模型调用失败带指数退避重试，但一旦已外发内容就不再重试（避免半截流重复），直接以 error 事件收尾。
  6. 思考流拆分：MiniMax 行内 <think> 标签由 ThinkSplitter 增量拆分（标签可能被切断在相邻 chunk，尾部疑似标签前缀的部分暂留缓冲区）；Qwen3 的 reasoning_content 由 ThinkingChatOpenAI 子类补采（langchain-openai 基类会丢弃该字段）。

四、对话式迭代的可靠性防御链（ADR 0004 / 0005）

已有文件后的用户对话轮是唯一进意图分类器（agent/intent.py）的入口：

  • 咨询类 → 只绑只读工具集（能力缺失代替劝说，物理上写不了文件），流式纯文本收尾，不产卡片、不核验、不入日志、不留快照；
  • 修改类 → 工程师智能体迭代，收尾经过多层防御：
层机制说明
1轮次产物终结出口submit_turn_result 是唯一合法收尾出口，模型必须显式申报本轮改动（intent / summary / changed_files）
2自洽性核验（工单 0025）比对「申报的改动集合」与「磁盘真实改动集合」，纯集合运算不看措辞；不一致回喂一次（轮级预算，防死循环）
3意图误判二次防线分类器把明确带改动动词的诉求判成 consult 时，用确定性关键词规则救回 modify_code
4超步兜底max_steps_exhausted 时磁盘已有的真实改动不被没收，照常收尾建快照
5零交付闸（工单 0029）团队工单执行轮磁盘零改动只有一条合法出口——经工单级确认回喂后的结构化 no_change；其余零改动一律按失败处置

五、记忆管理机制

没有用向量库做对话记忆（Milvus 只用于 RAG 模板检索），也没有 LangChain Memory 组件。记忆是分层设计：短期靠对话窗口，长期靠迭代日志，事实基准靠磁盘指纹。

5.1 第 1 层：对话历史（短期记忆）

  • 每条消息（用户话、智能体输出、工具事件、思考片段）全量落 SQLite Message 表，持久化永不截断，前端刷新可完整回看；
  • 喂给模型的只有 _llm_history 组装的最近 10 轮问答（agent_history_window=10），且按 kind 过滤：
    • event（工具事件）/ thinking（思考）/ ticket（工单进度）/ system 引导 → 不入上下文；
    • consensus / spec / tickets / prd（阶段定案产物）→ 以带前缀的 AIMessage 入上下文；
    • *_confirm（确认消息，含用户追加意见）→ 以 HumanMessage 入上下文，后续阶段可见。

5.2 第 2 层：迭代日志（长期记忆）

Project.iteration_log（JSON 列），按「改动」而非「对话轮」累积（工单 0026）：

  • 每轮成功收尾追加一条：{seq, user_text, user_goal(分类器蒸馏), files(真实触及文件), verdict, scope_verdict}；
  • 每轮开始读出并渲染进系统提示（build_system_prompt），弥补窗口截断的失忆，避免重复改或漏改；
  • 不截断、不聚合（注释明确算过 token 账：净开销持平或更短，不预先优化）；
  • 写入纪律：团队工单执行（record_iteration=False）不读也不写——内部编排不是用户对话轮，避免把工单指令当「用户说」污染后续提示；咨询轮无改动不入日志；超步兜底轮只要磁盘有真实改动也留一条（否则后续轮次无法理解磁盘现状）。

5.3 第 3 层：磁盘状态即事实基准（防「记忆过时」）

不信任模型的叙述性记忆，以磁盘为权威（工单 0022）：

  • 每轮开始扫描项目目录生成 file_summaries：路径 + 行数 + 内容哈希，注入系统提示。哈希的作用：若与记忆中的版本不同，说明记忆已过时，必须 read_file——模型不许凭记忆写 edit_file；
  • 同一份扫描复用为轮前指纹：轮末自洽性核验拿它与磁盘终态做集合比对，看磁盘不看措辞。

5.4 第 4 层：单轮内的临时记忆

run_generation 里的 messages 列表只在内存中活一轮（模型输出、ToolMessage 不断追加），不持久化；断流/取消时尽力把已流出的 thinking 片段落库，供刷新后回看诊断。

5.5 第 5 层：跨项目记忆（RAG）

Milvus Lite 知识库（seed:{key} 模板种子 + pub:{slug} 已发布应用）是跨项目经验库，经 search_templates 工具按需语义检索——服务生成质量，不服务对话连续性。

5.6 记忆分层总览

层载体生命周期注入方式
对话窗口SQLite Message 表全量持久化 / 只喂最近 10 轮langchain 消息列表
迭代日志Project.iteration_log JSON 列按改动累积、永不截断系统提示渲染
磁盘指纹每轮重扫（路径+行数+哈希）每轮刷新系统提示 + 轮末核验基准

六、成果出口：预览 / 发布 / 世界

生成落盘→ 项目快照（回滚 + Monaco 代码视图 / Diff，上限 50 版）→ 预览（/p/ 沙箱直出 + CSP sandbox 头）→ 发布（稳定公开链接，沉淀进 RAG）→ 应用世界画廊（浏览 + 一键克隆，失败事务性回滚）

七、SSE 事件协议（前后端契约）

事件含义
text / thinking正文 / 思考过程增量（打字机效果）
tool (start/done/error)工具调用卡片（参数超长只留摘要，结果截 500 字符）
clarify结构化澄清问题（选项卡片）
consensus / spec / tickets阶段定案产物卡片
ticket_progress团队模式逐单执行进度
done本轮结束（可携 verdict / warning / artifact 字段）
error失败（可携结构化 reason，如 max_steps_exhausted）
